## 3.0.0 (2026-11-27)

### ⚠️  Breaking Changes

- 3.0 is a breaking release; the [migration guide](https://taucad.github.io/three-viewport-gizmo/docs/migrating/) lists every change with the code that replaces it. In short: the package is ESM only, with camera-controls support in the `/camera-controls` subpath. The gizmo goes into the canvas's parent instead of `document.body`, extends `EventDispatcher` instead of `Object3D` (the scene object is `root`, the 26 targets are `targets`) and keeps one public `domElement` with state attributes instead of inline cursor, `z-index` and `border-radius`. Events carry a cause and a pose, turns run through `lookFrom()` and `turn()`, which return a promise of the outcome, and options are validated with coded errors. Views may roll unless `roll: false`, which keeps the 2.x upright behaviour. The gizmo is a keyboard tab stop. New: six up axes with `frontDirection`, controlled mode, limits, opposite click, the rounded cube and triad, and opt-in navigation buttons. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Ships the package as ES modules only. The UMD build and the `require` export are gone: `exports` now has `types` and `default` conditions, the package declares `sideEffects: false` and `engines.node >=20`, and the tarball includes the changelog. CommonJS consumers load it with `import()`. The repository no longer commits `dist/`; CDN users load the build from the npm tarball. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The `three` peer range starts at 0.167 (was 0.162): the type declarations import `WebGPURenderer` from `three/webgpu`, which three and `@types/three` ship from 0.167. `WebGPURenderer` draws the gizmo from three 0.171, and roll with OrbitControls still needs 0.168. CI checks 0.167, 0.168 and the latest three on every pull request. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- `ViewportGizmo` is a controller, not a scene object: it extends `EventDispatcher` instead of `Object3D`. Its drawable is the new read-only `root`, so `hostScene.add(gizmo)` is a type error, and `render()` takes `root` back if a host scene adopts it. Code that used the gizmo's `Object3D` side (`gizmo.add(...)`, `gizmo.children`, `gizmo.scale`, `renderer.compileAsync(gizmo, ...)`) moves to `gizmo.root`. The new read-only `targets` lists each target as data: name in the label frame, kind, direction and label. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- `ViewportGizmo` now runs on the 3.0 modules. Every click, drag and turn writes the camera through one pose write: `camera.position`, `camera.quaternion` and `camera.up`, then tells the attached controls about a new up. Events follow the 3.0 contract: `press` (`{ pressed }`) for every accepted press, `start`, `change` and `end` keyed by `cause` (`click`, `drag`, `key`, `navigation`, `api`) with a heading, a pose `{ direction, up }` and an outcome (`reached`, `interrupted`, `cancelled`, `unavailable`), `hoverchange` (`{ hovered }`, also when a turn moves a target under a still pointer), `attargetchange` and `invalidate`, which a render-on-demand host can render from alone. `end` balances `start` under `cancel()`, `pointercancel`, `enabled = false`, a structural `set()` and `dispose()`. `update()` no longer steps the controls, so it is safe inside a controls `change`; `render()` measures the gizmo's rectangle itself. State is read-only: `options`, `targets`, `hovered`, `dragging`, `animating`, `heading`, `atTarget`, `up`, `canRoll`, `viewport`; `enabled` is an accessor. The label up defaults to `camera.up` snapped to its nearest axis. The removed 2.x members `domUpdate()`, `cameraUpdate()`, `placement`, `animated` and `speed` throw `ViewportGizmoError` with code `REMOVED_MEMBER`, naming the replacement; constructing without a `document` throws `DOCUMENT_MISSING`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Freezes the 3.0 public contract: the root entry exports `ViewportGizmoError` with a `GizmoErrorCode`, and the 3.0 types for targets, poses, turns, outcomes, events, options, resolved options, controls, navigation and materials. "Target" replaces "axis" in every public name (`GizmoAxisOptions` is now `GizmoTargetOptions`), the label-frame front is the new `frontDirection` option, and the published types no longer import `utility-types` or `OrbitControls`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Options are validated and merged. `set(partial)` merges into the current options, so `set({ size: 64 })` keeps a cube a cube, and passing `undefined` returns a key to its default. A key the library does not know throws `ViewportGizmoError` with code `UNKNOWN_OPTION`, a wrong type or out-of-range value `INVALID_OPTION`, and the 2.x `up: 'z'` `REMOVED_OPTION` naming its replacement, `up: new Vector3(0, 0, 1)`. Values are no longer JSON-cloned: a `THREE.Color` or a function is kept as passed. `rounded-cube` changes only defaults and no longer overwrites `edges`, `corners` and per-target `scale` and `opacity` a caller passes. A face alias such as `front` merges over its axis key instead of replacing it, and styles only its own face. `animated` follows `prefers-reduced-motion` when it is not given. New options: `frontDirection`, `roll` (`true`, `false` or `'free'`), `poleEntry`, `oppositeOnRepeat`, `drag`, `limits`, `controlled`, `fieldOfView` (radians, in (0, 100°]), `navigation` and `triad`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Face names come from one label frame built from `up` and `frontDirection`, one of the 24 cardinal frames. The face-style alias, the face reported in events and the drawn label always name the same face: on a Z-up gizmo, `front: {...}` now styles the face labelled Front, where 2.3.0 styled the one labelled Back (and `back` the one labelled Front). `up` is read by direction within 1e-6 of a signed axis, so `(0, 0, 0.9999999)` is +Z and `(0, 0, -1)` is −Z, where 2.3.0 read both as +Y; a tilted `up`, or a `frontDirection` that is not a signed axis perpendicular to it, throws `ViewportGizmoError` with code `INVALID_FRAME`. A negative up keeps the 2.x front of its axis. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Turns follow the orbit up. A turn reads the camera's roll about its line of sight as a residual and eases it out with the other two angles, so a turn from a camera a host has rolled no longer jumps by the whole roll on its first frame, and a turn with no roll stays upright on every frame as in 2.3.0. A click keeps the signed axis nearest the current orbit up with `roll: true`, returns to the label up with `roll: false`, and turns by the single shortest rotation to an orientation resting on the target with `roll: 'free'`. Pole entry (`poleEntry`: `front` or `nearest`), the opposite view on a repeat click (`oppositeOnRepeat`), polar and azimuth `limits` in the orbit frame, relative turns with roll, side-triangle turns, `home` and `up: 'reset'` follow the same model for clicks, drags, keys, navigation buttons and the API. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- `attachControls` takes any controls of the structural `GizmoControls` shape and checks them: controls without a `target` vector, `update()` or a `change` event throw `ViewportGizmoError` with code `INVALID_OPTION`, naming the camera-controls adapter, instead of failing later on an undefined read. The gizmo copies the controls' `target` instead of sharing the vector. After a gizmo interaction the controls get back the `enabled` value they had, so controls the host disabled stay disabled. Numeric `minPolarAngle`, `maxPolarAngle`, `minAzimuthAngle` and `maxAzimuthAngle` on the controls are read as limits. After the gizmo changes `camera.up`, controls with `updateCameraUp()` are told, and `OrbitControls` and `MapControls` from three 0.168 have their orbit axis refreshed so the next drag orbits the new up; below three 0.168, `roll: true` with `OrbitControls` throws `ROLL_UNSUPPORTED` naming the three version. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- `controlled: true` now writes no camera (U4). Clicks, drags and flights report each pose in `change` as `{ direction, up }` and continue from the reported pose, so a host that applies it late or not at all never changes a turn. A host that applies the pose with `camera.lookAt` matches write mode frame for frame. The gizmo still disables attached controls while it turns, but in controlled mode it neither updates them nor calls `updateCameraUp()`: sync controls that keep their own state, such as camera-controls, after `end`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo's element is created once and kept for the gizmo's life. The library writes only its position, size, margin and `touch-action: none` inline; it no longer writes `cursor`, `z-index` or `border-radius`, nor the dead `id` style. Interaction state is reported as `data-hovered="face|edge|corner"`, `data-dragging` and `data-disabled`, for host CSS. Without a `container` the element goes into the canvas's parent, not `document.body`; a selector that matches nothing, or a canvas with no parent, throws `ViewportGizmoError` with code `CONTAINER_MISSING`. To restore the 2.x look: `.your-class { z-index: 1000; border-radius: 100%; } .your-class[data-hovered] { cursor: pointer; }`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo's pointer input follows one captured pointer at a time and the primary button only: a second finger, another device or a right-button press does nothing, and the right button keeps its context menu. A browser `pointercancel` ends the gesture as cancelled instead of leaving it stuck, the hit rectangle is measured at each press so a page scroll no longer shifts picks, hover never runs for touch, and a second click within 400 ms on the same spot (within 5 px) is classified as a double-click whatever target it hits. A wheel over the gizmo can be handed to the host's canvas so its controls keep zooming. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Hover and click are tested analytically: one pointer ray against the gizmo's box (sharp for `cube`, rounded for `rounded-cube`) or the sphere's discs, classified into one of the 26 targets, with 2.3.0's corner-over-face priority. Hit regions no longer depend on the render meshes, their `smoothness` or a host-replaced geometry, and no longer on the gizmo camera having rendered, so a hover or click before the first frame lands. The closed box also answers in the gaps between 2.3.0's cube tiles, where 2.3.0 hit nothing. A disabled target is never hit. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo's draw keeps the host's frame outside its rectangle on both backends. It always scissors its own rectangle, clears nothing, and resets depth inside the rectangle with a colourless quad drawn first, so depth outside the rectangle survives for host draws after the gizmo: before, WebGL cleared the whole depth buffer when the host's scissor test was off, and WebGPU always did. It works with standard, reversed and logarithmic depth. The host's viewport, scissor, scissor test and `autoClear` are read when the gizmo draws and restored afterwards, even if the draw throws, so a viewport the host changed since the last layout pass is no longer reset to a stale one. When the renderer has a render target, the gizmo writes its rectangle to that target's `viewport` and `scissor`, scaled to the target's pixels, and restores them, so hosts no longer set them by hand. The rectangle is measured from the gizmo's element at each draw. The depth reset adds one draw per frame and, on WebGPU only, one pipeline. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo's scene is built once per structural option change and updated in place for every other one. It disposes only the materials, geometries and textures it created, so a sprite, material or texture a host adds under the gizmo, or a material a host returns from `onMaterial`, survives `dispose()`. Targets of equal style share one material: a cube draws with at most 16, its 20 edges and corners share one hover material, and hovering swaps to a material that compiles the same program or pipeline. Every gizmo material is `toneMapped: false` with fixed transparency and depth-write flags. Disabling a face, the edges, the corners, an axis line or the background hides it without a rebuild. Face labels and edges are oriented by the label frame, so the Top and Bottom labels read upright on every up axis. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- A gizmo now adds at most two programs (WebGL) or pipelines (WebGPU), down from three on the sphere and four on the cubes, and hovering compiles none. Every mesh it draws (labelled faces, edges, corners, axis lines and background) uses one basic material program: a map everywhere, a 1×1 white texture where there is no label, and vertex colours on. Showing the axis triad adds none: its labels are camera-facing quads on that program instead of sprites. The sphere's sprites are the other program. On WebGPU the cubes' background is the second pipeline, because it does not write depth. The cubes' background now draws the front side of mirrored faces instead of `BackSide`. Every pixel is unchanged. A material handed to `onMaterial` for an edge or corner now has `map` set to that white texture and `vertexColors` on. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Labels are drawn one small texture per label instead of one shared atlas: a face gets its own texture, and a hover texture only where its hover colour, label colour or border differs. The default cube holds 12 label textures, about 1 MB, instead of 2.3.0's clones of one atlas (13.4 MB of WebGPU texture memory after hovering). Each texture is sized from `size` and the device pixel ratio unless `resolution` is set, so labels stay sharp on high-DPI screens; `resolution` has no fixed default any more. Rounded-cube face labels fill their texture edge to edge. `font.size` is in CSS pixels as documented. Text is centred on its ink, and the label no longer disappears where the browser reports no `fontBoundingBoxDescent` (Firefox before 116). A web font that finishes loading after construction redraws the labels with no `set()`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The axis lines are one mesh of six cylinders with one vertex-coloured basic material, drawn in one call, instead of `Line2` with `LineMaterial` or `Line2NodeMaterial`. Their width is `lineWidth` CSS pixels in the gizmo's own rectangle, so it no longer depends on the window size at construction and stays the same when the host canvas resizes, on both renderers. The new scene path imports nothing from `three/webgpu` or `three/addons/lines/`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))

### 🚀 Features

- Turns have a promise API: `lookFrom(view, { animated, up })` and `turn({ toward })` or `turn({ azimuth, polar, roll })` return a promise of the `end` payload, which resolves with `reached`, `interrupted` (`by` the newer turn, click or drag), `cancelled` (`cancel`, `pointercancel`, `disabled`, `set`, `dispose`) or `unavailable` (`roll-off`, with no event and the running turn left alone). `atTarget` is set after a click, a quarter turn and a roll (a rolled edge or corner stays at its target) and cleared by a drag or a host camera move. A double-click on the cube lands upright on the view the first click turned to and never turns to the opposite target; with `roll: false` the second click now keeps the first click's turn instead of turning back. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The `fieldOfView` option sets the gizmo's own camera's field of view in radians (not three.js's degree `fov`); it moves the camera to keep the cube's apparent size and rebuilds no geometry or material. `compile()` warms up the gizmo's scene with its own camera for the renderer's current render target, on WebGL and WebGPU. These replace a host's reach into the private `_camera` and its own `compileAsync` call on the gizmo. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo's element is keyboard operable. It is a focusable `role="application"` (`aria-roledescription` "view cube" or "view sphere") whose `aria-label` reads the view and the roll ("Front, rolled 90° clockwise", or "Near Top Front Right" off a target), with a visually hidden `role="status"` first child that announces a reached key turn. While it has focus, the arrow keys step to the neighbouring view on that side of the screen (45° toward it, snapped to the nearest of the 26 targets), digits 1 to 6 (top row or keypad) look from Front, Back, Left, Right, Top and Bottom, Home goes home upright, and Shift with Right or Left rolls a quarter turn when `canRoll`. Every key runs `lookFrom` or `turn` with cause `key`; a consumed key is `preventDefault`ed and still propagates; Ctrl, Meta and Alt chords, letters, Escape, Enter, Space and IME input are left to the page. `enabled = false` writes `tabindex="-1"` and `aria-disabled="true"` and takes no key. A pointer press on the gizmo no longer moves focus. Hosts with their own capture-phase arrow keys should treat `[role=application]` as a control that keeps its arrow keys. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo can draw its own navigation buttons, off by default: `navigation: { enabled: true }` adds seven real `<button>`s to its element on a 3 x 3 grid around the cube, side triangles at a face view, roll arrows at any target while `canRoll`, and Home at every view, each a 16 px chip with a 24 px hit area. They show on hover, on focus within the element and always on a device without hover (`reveal: 'always'` shows them always), and `sides`, `roll` and `home` switch each kind off. Every press is a `turn` or `lookFrom` with cause `navigation`. The grid sits at `--viewport-gizmo-anchor`, computed from the cube's silhouette, and the colours follow the cube's style behind the `--viewport-gizmo-button-background`, `-ring`, `-ring-hover`, `-color` and `-focus-ring` custom properties. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The cube types gain a built-in axis triad, off by default: `triad: { enabled: true }` draws world +X, +Y and +Z from the cube's corner with an X, Y or Z label past each tip in the axis colour (`triad.colors`), and shrinks the cube to 0.7 to give it room. Each line is a camera-facing ribbon with a feathered edge, smooth without MSAA. It switches on and off through `set({ triad })` as a cheap change, with no rebuild, and adds six draws while shown (three lines, three labels). The sphere has no triad. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The `rounded-cube` is one seamless closed rounded box. Its 26 targets are pieces of that box with no gap or seam between them, drawn as clean rectangles with exactly the rounded patches as corners. A corner still wins a pointer a little way into the faces and edges around it (see `corners.hitSize`), and hovering there lights the corner's patch. The box draws at most 15,000 triangles at any `smoothness`. Its faces and corners default to white and its edges to `#eeeeee`. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Add `corners.hitSize` and `edges.hitSize`: how far in from the cube's edge, in gizmo units (a face's half-width is 1), a pointer still lands on a corner or an edge. They change the hit test only; the drawn pieces and their hover highlight stay the same, and changing either through `set()` rebuilds nothing. The `sphere` ignores both. ([#69](https://github.com/taucad/three-viewport-gizmo/pull/69))

  - `cube`: corners 0.35 and edges 0.3 by default, the 2.3.0 hit regions. Edges are never narrower than the gap between the face tiles.
  - `rounded-cube`: corners `min(radius + 0.2, (1 + radius) / 2)` by default, exactly the 3.0.0-beta.3 corner band at every radius; edges `min(max(radius + 0.1, 0.15), (1 + radius) / 2)`: the drawn strip plus a 0.1 band, as the corners have their 0.2, never under 0.15 and never past the inner half of a face. Both are clamped to `[radius, 1)`.

  Behaviour change since 3.0.0-beta.3: the `rounded-cube`'s edges now catch a pointer up to 0.1 beyond their drawn strip (0.15 in from the cube's edge below `radius` 0.05), as its corners already did, instead of only on the strip. At the default `radius` 0.3 an edge reaches 0.4 in and the face keeps its inner 60 %. Pass `edges: { hitSize: radius }` for the drawn strip only (the 3.0.0-beta.3 hit region), or `edges: { hitSize: Math.max(radius, 0.15) }` for this option's earlier default.

- camera-controls attaches through `cameraControls(controls)` from the new `@taulabs/three-viewport-gizmo/camera-controls` subpath: `gizmo.attachControls(cameraControls(controls))` replaces the hand-written event glue. The adapter hands camera-controls the pose the gizmo wrote, keeps a copy of its target, maps `enabled` and its polar and azimuth limits, and forwards `updateCameraUp()`, so `roll` defaults on with camera-controls. `camera-controls` is an optional peer dependency (`^3.0.0`); the root entry and its types never import it. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- The gizmo element's inline `width`, `height` and `margin` now read the custom properties `--viewport-gizmo-width`, `--viewport-gizmo-height` and `--viewport-gizmo-margin`, falling back to the `size` and `offset` options. A host class can resize or reposition the gizmo without `!important`, and the package still ships no stylesheet. ([#63](https://github.com/taucad/three-viewport-gizmo/pull/63))

### 🩹 Fixes

- The sphere's background is a camera-facing disc of 128 triangles instead of a 64 × 64 back-facing sphere of 8,064. It draws the same circle behind the axis lines, and follows `background` and `background.hover` the same way; at oblique orientations its rim is the exact circle where the sphere's tessellated silhouette lost up to 48 edge pixels in a 256 px gizmo. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Since 3.0.0-beta.4, the pointer hits the target drawn under it at every `fieldOfView`, on `WebGPURenderer` and `WebGLRenderer`, with or without `reversedDepthBuffer`. A renderer rewrites the gizmo camera's projection when it draws (WebGPU clip depth, reversed depth); the hit test now reads that same camera in whichever convention it carries, where it assumed WebGL's and, under reversed depth, picked the face behind the one drawn below 26° (and on the sphere at any angle). The depth reset also stays behind the gizmo at very narrow angles, where it fell in front of the near plane and left the host's depth inside the gizmo's rectangle. ([#70](https://github.com/taucad/three-viewport-gizmo/pull/70))
- `compile()` logs nothing on a WebGL device without `KHR_parallel_shader_compile`: it compiles synchronously there instead of through three's `compileAsync`, which warned that the extension is not supported. ([#60](https://github.com/taucad/three-viewport-gizmo/pull/60))
- Since 3.0.0-beta.5, the gizmo's accessible name follows every pose it observes. It was rewritten only when the view moved onto or off a target, so a pose the host applied off a target (a saved pose adopted after construction, the host's own controls, controlled mode) kept the previous "Near …" name, a roll the host applied at an edge or corner kept the previous roll, and `set()` that relabelled a face kept the old label in `aria-label` and in `atTarget`. The name is now derived from the pose wherever the gizmo observes it (`update()`, the end of a turn, `set()`), and `aria-label` is written only when the name changes, so an observed turn that keeps the name allocates nothing for it. ([#79](https://github.com/taucad/three-viewport-gizmo/pull/79))
- Since 3.0.0-beta.2, the axis triad's lines are smooth on a single-sample host (Tau's WebGPU node pipeline, phones): each is a feathered camera-facing ribbon instead of a hard-edged cylinder, and the triad adds six draws (three lines, three labels) instead of four. Since 3.0.0-beta.2, the navigation buttons no longer show their focus ring at rest in Safari (WebKit reads `outline: none` back as "medium", which a restyle took for a focused button); the ring now shows only on the `:focus-visible` button and sits snug around its chip. ([#65](https://github.com/taucad/three-viewport-gizmo/pull/65))
- Since 3.0.0-beta.1, the navigation buttons are easier to reach. On the sphere, the corner buttons (Home and the rolls) sit on the diagonal at the side buttons' distance, overlapping the element's corner, instead of on the cube's square grid far outside it; the element also carries `--viewport-gizmo-anchor-corner`, their per-axis distance from its centre. With `reveal: "hover"`, the buttons stay for 400 ms after the pointer leaves the element, so it can cross the gap to one outside. The sphere's buttons are white chips ringed in the up axis's colour; a cube's chip takes its edge colour only when edges are drawn. ([#63](https://github.com/taucad/three-viewport-gizmo/pull/63))

  The button grid follows the element's measured height after each render, so a gizmo resized from CSS keeps its buttons clear of it.

  The buttons no longer set `cursor: pointer`: they show the default cursor, like the cube, and a host can style `[data-navigation]` buttons without `!important`.

- Since 3.0.0-beta.1, the `rounded-cube`'s corners default to white again, like its faces, as in 2.3.0; its edges stay `#eeeeee`. 3.0.0-beta.0 drew the corners in the edges' grey. ([#63](https://github.com/taucad/three-viewport-gizmo/pull/63))
- Since 3.0.0-beta.1, the `rounded-cube`'s faces and edges are drawn as clean rectangles: its drawn corners are exactly the rounded corner patches. Before, a corner reached a little way into the three faces and edges around it (2.3.0's corner-over-face click priority), which cut a square notch out of every face. A corner still wins clicks a little way into them; only the drawing changed. ([#63](https://github.com/taucad/three-viewport-gizmo/pull/63))
- Since 3.0.0-beta.3, the `rounded-cube`'s corners are easy to hover and click again at any `radius`. 3.0.0-beta.1 shrank a corner's hit region to its rounded patch, so a small `radius` (0.05) left each corner under 1% of the view; the hit region again reaches 0.2 into the faces and edges around the patch, as in 2.3.0 and beta.0 (it keeps at least the inner half of each face, so a large `radius` no longer turns the whole cube into corners). The faces and edges are still drawn as clean rectangles: hovering inside the band lights the corner's rounded patch. ([#67](https://github.com/taucad/three-viewport-gizmo/pull/67))
- Since 3.0.0-beta.5, `render()` no longer reads the gizmo's rectangle from layout on every frame. Measuring with `getBoundingClientRect` every frame allocated 32 B a frame, and 76 to 82 B at a subpixel offset (each fractional coordinate comes out of the DOM as a new number), over the 64 B idle budget. The gizmo now compares the whole-pixel positions (offsets summed up each `offsetParent` chain) and sizes of its element and the canvas each frame, which allocates nothing, and measures exactly when one changed or when the window resizes (zoom included), anything scrolls, either box changes size by a fraction of a pixel (`ResizeObserver`, from the next frame) or `set()` is called (`set({})` included). The drawn rectangle is the same subpixel rectangle as before, picked up on the same frame for a container, element or canvas resize, a move of a pixel or more (also of a positioned container that holds only one of them), a scroll or a pixel-ratio change. Only a move of less than half a CSS pixel that changes no size, or a move made purely by a CSS transform, waits for the next of those signals; `set({})` picks it up on the next frame, and asks for one (`invalidate`). ([#83](https://github.com/taucad/three-viewport-gizmo/pull/83))

  Also since 3.0.0-beta.5, hidden axis lines no longer cost triangles. They were collapsed to the origin and still drawn; the shown lines now come first in the lines' index and the draw range ends after them, so the sphere with its default three lines draws 238 triangles instead of 334 (the budget is 300), with the same pixels on WebGL and WebGPU.

  The sphere's background merges its geometries with the gizmo's own helper, so `three/addons/utils/BufferGeometryUtils.js` is no longer imported (about 1 kB less gzip in an app that does not use it otherwise).

- Since 3.0.0-beta.5, the rounded cube keeps its drawn size under any `fieldOfView`, with or without the triad. The camera distance held the projected size of one depth, the unit cube's front face, but the rounded cube's outline runs round its bevel, nearer the centre (`1 − radius`) and closer to the camera as the camera comes closer, and the triad shrinks the scene to 0.7: at radius 0.3 with the triad the cube was 10 % larger at 0.1° and 20 % smaller at 90° than at 26°. The distance is now solved from the outline the gizmo draws, so the rounded cube stays within a pixel of its 26° size from 0.1° to 90°; at 26° nothing changes (distance 7). The triad's line width and label texels follow the same distance. ([#83](https://github.com/taucad/three-viewport-gizmo/pull/83))
- Since 3.0.0-beta.0, a web font that finishes loading after construction redraws the labels in WebKit browsers too. The labels waited for `document.fonts` `loadingdone`, which WebKit never fires for a `FontFace` the page adds and then loads, so they kept the fallback font until the next `set()`. They now redraw once each time a round of font loading ends, in every engine, whether the host loaded a `FontFace` or drawing in a CSS `@font-face` family started the load: on `loading`, they wait for every face still loading to settle (the set's `ready` only when none is), then for one animation frame, so the canvas draws in the new face. `dispose()` stops it, a load still pending included. ([#84](https://github.com/taucad/three-viewport-gizmo/pull/84))
- Since 3.0.0-beta.0, a press or turn on the gizmo stops the motion the attached controls keep up after a drag: OrbitControls' and MapControls' damping, TrackballControls' inertia and ArcballControls' animation (three 0.168 or later for OrbitControls and TrackballControls). Disabling the controls stopped their input but not that motion, so a gizmo click right after a flick on the canvas reported `reached` and the camera then drifted off the view; ArcballControls, whose animation is on by default, did so in Safari after an ordinary drag. ([#84](https://github.com/taucad/three-viewport-gizmo/pull/84))
- Since 3.0.0-beta.5, a frame drawn with the triad depends only on the camera pose and the options, so the first frame back at a pose matches the frame drawn there before to the byte, on WebGL and WebGPU. Since 3.0.0-beta.2 the triad's lines turned to face the camera in `onBeforeRender`, after both renderers had sorted the frame from each line's world matrix, which was then still the previous frame's. At a view where two lines sit at the same depth (Tau's home view, where X and Z do) the order they were drawn in, and so a few pixels where they cross, followed the pose of the frame before. The lines, the triad's labels and the sphere's background disc now turn to the gizmo's camera in the gizmo scene's `onBeforeRender`, which both renderers call after updating world matrices and before building the render list; the turns are the same, so frames that did not depend on history draw the same pixels. ([#85](https://github.com/taucad/three-viewport-gizmo/pull/85))

  On `WebGPURenderer` before three r186, three's own `NodeMaterialObserver` can also draw an object with a previous frame's transform after the draw order changes (its first check each frame skipped syncing its cache), which a pose change can do to any gizmo part; three r186 fixes it, and a host on an earlier three needs that fix in three.

- Since 3.0.0-beta.5, a gizmo laid out off the canvas, or off the host's render target, draws nothing and no longer fails on WebGPU. A gizmo whose container is not the canvas's can sit outside it (Tau's container is `document.body`); three clamps only a scissor's far edges, so the gizmo's scissor kept an origin outside the target, and WebGPU rejected the frame (`Scissor rect … is not contained in the render area`). `render()` now skips the draw, touching no renderer state, when the rectangle misses the canvas or target, and when it is partly off, scissors to the part on it while the viewport keeps the whole rectangle, so the gizmo is cut at the edge rather than squashed. Hit testing is unchanged. ([#85](https://github.com/taucad/three-viewport-gizmo/pull/85))
- Since 3.0.0-beta.6, the classic `cube` keeps its drawn size under any `fieldOfView` too, with or without the triad, as the rounded cube does: face-on, its width stays within a pixel of its 26° width from 0.1° to 100°, where it grew by 3 % toward 0.1° and shrank by 5 % at 90°. Its width is bounded by its background's side plates, seen from inside, and at narrow angles by its corner plates, which turn away from a camera that comes close; the camera distance is now solved from what the gizmo draws at that distance, each one-sided plate counted only from where it faces the camera, instead of 2.3.0's unit front edge. At 26° nothing changes (distance 7). The triad's line width and label texels follow the same distance. ([#90](https://github.com/taucad/three-viewport-gizmo/pull/90))
